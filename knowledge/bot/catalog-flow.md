# Catalog flow

`src/core/catalogFlow.js` is the largest bot module (about 17k lines). It holds the detailed commercial conversation state machine: catalog selection/disambiguation, inquiry/order capture, product line items, pricing/HSN handling, updates, approval/stage gates, generated/system PO behavior, and response templates.

## Safe navigation
Search within the file by exported function, intent/state key, or user-visible response instead of reading it linearly. Trace each state transition to the Supabase helper and `pendingStateManager` call before changing it.

## Invariants
- Preserve active/pending flow state across follow-up messages and intentional flow switching.
- Do not bypass stage/PO validation to make a prompt “work”.
- Revalidate items/prices/server state on writes; user-provided state is stale or incomplete.
- Keep response identity and field terms compatible with the UI and retrieval tools.
- Inquiry payment terms and preferred brand accept only Immediate, Advance, 30 Days, 45 Days, 60 Days, LC, BG, PDC and TATA, JSW, AM/NS India, SAIL, NMDC, Apollo, Others. A close typo maps to that option. Orders and visits keep their own payment-term text.
- Customer name matching verifies against assigned accounts: if similarity is >= 70%, the bot auto-proceeds; if < 70%, the bot pauses with a validation prompt asking "Do you want to continue with the fetched customer name?" with a "Yes" button and up to 3 highest-matching accounts from the assigned customer list. Numbers 1–3 select from that list.
- If a customer is already registered under another representative, the current draft is blocked.
  The response preserves the ownership warning and offers only `Discard Draft`; it must not
  invite a replacement customer name or allow arbitrary text to resume that draft.
- When an unrecognized product is entered, do not fabricate a fallback HSN (`72083840`); leave HSN empty if undetected, present catalog suggestions alongside the `Add Product` button (`btn_add_product`), and allow saving a custom product to `products` via `catalog_implicit_prod_add|<RETURN_INTENT>` using only user-entered product name and specs before resuming the inquiry/order draft.
- Update Inquiry and Log Order use `src/core/inquiryScope.js`. WhatsApp and the dashboard assistant call this same catalog. A row stays when the last 10 digits of the stored salesperson phone, the sender phone, the linked deal's salesperson phone, or the active customer owner are in the caller's scope. An empty salesperson phone does not hide the row. Won and lost rows stay in Update Inquiry. Log Order keeps its own stage filter and still leaves purchase-order rows out.
- An `INQ-` or `DEAL-` code, typed alone or inside a sentence, is matched against that set. A code that does not match is not searched as a customer name.
- A quantity save writes the new quantity onto the existing line through `applyCommercialLines` in `src/core/tonnageReview.js`, then `tonnageReviewPatch`. `original_unit` stays, and a manual weight stays on piece units. A real MT change on Price Ready sets `awaiting_price` and opens the review, which the procurement Inquiries bell lists. `1000 KG` and `1 MT` do not. A rate, note, delivery, or payment edit does not. While the review is open, the deal stage stays where it is. The badge stored on the open card, such as Price Ready, Awaiting Price, or Unavailable, is the current label and is not a stage edit. Price Quote and Quoted still move the deal to Quoted.

`em-os-bot/test/regression/issue-chatbot-inquiry-update.test.js` covers the sender-only list, the `INQ-` lookup, and a Price Ready quantity change that reopens Awaiting Price without moving the deal to Price Quote. `issue-update-inquiry-quantity-review.test.js` covers the same save when the open card still carries the Price Ready badge. `issue-update-inquiry-price-save.test.js` covers a component change whose pricing `line_key` is not the deal item id: the confirmation shows the resulting rate, and the save updates that pricing row in place. Run focused scripts under `scripts/test-*catalog*`, `test-*order*`, `test-*inquiry*`, and `test-*update*` in a safe environment after changes.

Update Inquiry renders the dashboard badge precedence: Awaiting Price, Price Ready, and Unavailable override the pipeline stage; otherwise it shows New Inquiry, Price Quote, Negotiation, On Hold, Won, or Lost. The selected card and the save confirmation list every material from the deal items, then the inquiry items, then the AI lines. Each material shows its quantity and `Base ₹… + Transport ₹… + Loading ₹… + Credit ₹… + Margin ₹… = Rate ₹…/MT`. The displayed base is the sales base, or the procurement base when sales has not set one. A blank credit shows as ₹0. An unavailable line stays Unavailable. The seven-row index does not include prices. Except for Won and Lost, the salesperson can change base, transport, loading, credit, or margin for a named material in this same flow. Only the named components change. A chat base is stored as `sales_base_price_per_mt` and does not replace `procurement_base_price_per_mt`. A message that only gives a rate sets the margin when that margin is zero or more; otherwise the bot asks which component to change. The save confirmation shows that same breakdown with the new components and the resulting rate before Save. The sell rate is recomputed with the existing formula and written onto the existing `inquiry_line_pricing` row, keeping its `line_key` and omitting `id` and `created_at`, and onto `deal_items.rate`. After a priced save the inquiry is `sales_priced`. Negotiation, On Hold, Won, and Lost keep their stage. The chat does not send the decline email. Add Price to Inquiry and procurement base-price editing stay on their own paths.

Update Inquiry lists the same genuine inquiries the salesperson dashboard lists, seven per page, newest first. The inquiry code is `INQ-` plus the first six characters of the inquiry id, uppercased, the same formula as the Inquiries table. The line leads with that row's procurement number: `PR-10268 | INQ-C7B9F8 | Customer | items | status | date`. A blank `inquiry_type`, a purchase order, and text that mentions a PO stay in the list. A deal with no inquiry is not given an inquiry number. `Next` loads the next seven, and a row number, `INQ-` code, procurement number, or pasted list line selects that inquiry without general retrieval. Won and Lost rows remain visible; their price and stage fields are read-only. Closed, completed, and cancelled inquiries also refuse a price or stage change.

The AI Assistant identity comes from the API JWT. The API forwards that employee's phone to the bot. Candidate inquiries are loaded without selecting `display_stage`, because that value is calculated from the linked deal and inquiry stage. A missing optional pricing column is retried without that column. Update Inquiry then keeps the dashboard's genuine set, including blank inquiry types and purchase orders, and filters it in memory by normalized sender, salesperson, linked-deal salesperson, and customer-owner assignments. Log Order still drops purchase orders in the query. Both lists are shown seven at a time.
