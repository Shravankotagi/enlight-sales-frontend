# KRA, visits, and complaints

`KraModule` groups operational KRA dashboard, logs, action queue, visits, and complaints. Core tables are `kra_logs`, `customer_visits`, `followup_tasks`, `complaints`, and `complaint_attachments`.

The dashboard uses `/kra/dashboard`, `/kra/sheets`, `/kra/logs`, `/kra/action-queue`; visit endpoints `/kra/visits`, `/kra/visits/otp/request`, `/kra/visits/otp/verify`, and `/kra/visits/reverse-geocode` (Google Geocoding building name and street, plus city); complaint endpoints `/kra/complaints`. New dashboard visits require a consumed phone-verification token, a GPS photo, and the standardized brand and payment lists. Customer type includes Other, which requires `customer_type_other`. A new visit's next purchase date and follow-up date must be today or later. A salesperson can set follow_up_status to completed or pending on a visit they own, and cannot otherwise update the visit. A failed visit-code send logs Meta's error code, subcode, and message with the phone reduced to its last four digits. The code is sent with the approved WhatsApp Authentication template `WHATSAPP_VISIT_OTP_TEMPLATE`, so the customer does not need a chat in the last 24 hours. Meta `131026` tells them the number could not be reached. Any other code returns that code and Meta's message in the 400, with long digit runs removed. A new bot visit uses the same phone-code table before saving. The bot still writes the visit row itself. Preserve exact follow-up status/date semantics and authorization filtering when adding fields. See [../../flows/kra-computation.md](../flows/kra-computation.md) and [../../flows/visit-lifecycle-and-followups.md](../flows/visit-lifecycle-and-followups.md).
