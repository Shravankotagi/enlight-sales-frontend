# Auth and OTP

`AuthModule` exposes OTP request/verification through `auth.controller.ts` and `auth.service.ts`; `OtpModule` owns OTP persistence/lifecycle through `otp_sessions`. The frontend calls `/auth/request-otp` and `/auth/verify-otp`, normalizing Indian phone numbers with the `91` prefix in `src/lib/api.ts`. An unknown phone returns `Phone number not registered. Contact admin.` The login form shows that sentence, not the HTTP status text.

Successful auth produces the token consumed by the global frontend Axios interceptor as `Authorization: Bearer …`. The OTP JWT includes `sid` (one id per successful login). `POST /auth/logout` accepts `{ reason: 'manual' | 'session_expired' }`, verifies the bearer token with `ignoreExpiration`, and writes at most one Auth logout row for that `sid`. A bad token still returns 200 and writes nothing. The dashboard also logs out after 30 minutes without mouse, key, click, scroll, or touch input. OTP employee JWTs are distinct from Supabase Auth tokens used by legacy/admin endpoints. The token proves who logged in. `JwtAuthGuard` then loads the current role and permissions from the database. See [roles and permissions](roles-and-permissions.md). `GET /auth/me` returns that result to the dashboard. Backend authorization is layered: the relevant token guard, employee identity, and role/scope checks. Do not treat a frontend filter as authorization.

`request-otp` is an externally reachable boundary: never return a development OTP or credentials in production responses/logs.
